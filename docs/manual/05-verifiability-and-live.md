# 05 · Verifiability — accountability without retention

[Verifiability](12-glossary.md) is the axis both the [claim plane](12-glossary.md) (`03`) and the [distribution plane](12-glossary.md) (`04`) read from, and both chapters point here rather than defining it themselves. `03` states the two claim-plane rules that key on this axis — `deny-damage-assessment-without-retained-evidence` and `allow-facility-context-re-derivable` — and explicitly defers what a live source and its record are to this chapter; `04` states that `license` is the distribution plane's third artifact attribute, checked separately from `resolution_cap` and `audience` because a third party's terms are not this project's own judgment to fold into the other two. This chapter is where the axis itself gets defined, and where the record `license: project` protects — built for a lookup this project is contractually forbidden to retain — gets explained end to end.

The live lookup mechanism itself, `src/geosteward/live/`, sits at the gateway boundary chapter `07` covers end to end, and its rendered form is a chip chapter `08` describes; this chapter covers neither the request lifecycle nor the UI, only the two things that make a non-retainable lookup accountable: the axis that classifies it, and the record that survives it. One thing to hold onto while reading everything below: the axis, the two regimes, the record, and the test that checks it are all demonstrated here against a fake source or an in-process stub, never against Google. The final section states plainly what that does and does not establish; no sentence before it should be read as evidence the mechanism has run against a live API.

> **中文。** [可验证性（retained 留存 / re-derivable 可复现 / cited-only 仅可引证）](12-glossary.md)是断言平面（`03`）与发布平面（`04`）共同读取的一根轴，但这两章都没有给出它的定义，而是把定义留给了本章：`03` 讲了两条挂在这根轴上的断言平面规则——`deny-damage-assessment-without-retained-evidence` 与
> `allow-facility-context-re-derivable`——并明确把"实时数据源本身及其记录是什么"留给本章；`04` 讲了 `license` 是发布平面的第三个制品属性，之所以和 `resolution_cap`、`audience` 分开检查，是因为第三方的条款不是本项目自己能去判断的事，不能和另外两项混在一起。本章要讲清楚这根轴本身是什么，以及 `license: project` 所保护的这份记录——为一次本项目被合同禁止留存的查询而建——具体长什么样。
>
> 这套实时查询机制本身（`src/geosteward/live/`）位于 `07` 章完整讲述的网关边界上，它渲染出来的样子是 `08` 章描述的一个小标签；本章既不讲请求生命周期也不讲界面，只讲让一次不可留存的查询变得可问责的两件事：给它分类的那根轴，以及它留下的、能够存活下来的记录。读下面的内容时请先记住一点：这根轴、两种机制、这份记录，以及检查它的那个测试，全部都只针对一个假数据源或一个进程内的桩（stub）做过验证，从未针对 Google 真实运行过。最后一节会把这一点讲清楚，说明这具体证明了什么、又没有证明什么；在读到那一节之前，不应把前面任何一句话当作这套机制已经对接过实时 API 的证据。

## The problem: forbidden to keep the evidence

Google Maps Platform's terms forbid retaining Maps Content — the names, ratings, reviews, photos, and phone numbers a Places lookup returns — while GeoSteward's own process validity works the opposite way, proving traceability by hashing and freezing every input it uses (`docs/design/specs/2026-08-20-non-retainable-evidence-design.md`, §1). The two are structurally incompatible: running a Google-derived source through the same hash-and-freeze pipeline as every other source would make the pipeline itself the violation. That incompatibility is not a blocker to route around; it is what turns an ordinary integration task into a real question the rest of this chapter tries to answer — when a project is contractually forbidden from retaining the evidence, what makes a claim resting on it accountable?

> **中文。** Google Maps Platform（谷歌地图平台）的服务条款禁止留存 Maps Content——也就是一次 Places 查询返回的地点名称、评分、评论、照片、电话号码这些具体内容——而 GeoSteward 自身证明过程有效性的方式恰恰相反：对它用到的每一项输入做哈希、冻结（`docs/design/specs/2026-08-20-non-retainable-evidence-design.md` 第 1 节）。这两者在结构上互不相容：如果把一个源自 Google 的数据源塞进和其他每一个数据源一样的"哈希再冻结"流水线，流水线本身就会构成违约。这种不相容不是一个绕过去就完事的障碍——它把一件原本平常的集成工作，变成了本章接下来要回答的一个真实问题：当一个项目被合同明确禁止留存证据时，建立在这份证据之上的断言，靠什么才算得上问责？

## A third axis, orthogonal to tier

`verifiability_rank(value: str) -> int` and `weakest(values: Any) -> str` in `src/geosteward/harness/policy.py` implement the axis this chapter is named for. `VERIFIABILITY_ORDER = ("cited-only", "re-derivable", "retained")` is a tuple whose index doubles as a strength rank, so `retained` outranks `re-derivable` outranks `cited-only`, and `weakest` returns the minimum rank across every source a claim draws on — the [weakest-link](12-glossary.md) rule — rather than the maximum or an average. Where a claim draws on both a hashed grid and a live lookup, the result is `re-derivable`, not `retained`, because taking the stronger of the two would let the retained half launder the live half into a standing it did not earn on its own.

This axis is not a fourth rung added on top of [tier](12-glossary.md), and `policy.py`'s own comment states the reason directly: tier encodes how fresh and how deep the evidence is — nationwide watch, tile-level analysis, cross-view evidence — while verifiability encodes something tier says nothing about, namely what a *reader*, not the project, can independently do to check a piece of support. A Places lookup can answer a facility question about a place this minute, at the finest resolution the source supports, and still sit at the bottom of this axis, because nobody without a Google Maps Platform key can replay it. Current and accurate is a tier question; checkable by someone outside the project is a verifiability question, and the same fact can score high on one and low on the other at the same time.

> **中文。** `src/geosteward/harness/policy.py` 里的 `verifiability_rank(value: str) -> int` 和 `weakest(values: Any) -> str` 实现了本章标题讲的这根轴。`VERIFIABILITY_ORDER = ("cited-only", "re-derivable", "retained")` 是一个元组，它的下标同时充当强度等级，于是 `retained`（留存）强于 `re-derivable`（可复现）强于
> `cited-only`（仅可引证）；`weakest` 取一个断言所依赖的所有来源里等级最低的那个——短板原则（weakest-link）——而不是取最高的或者做平均。当一个断言同时依赖一份留存的哈希网格和一次实时查询时，结果是 `re-derivable`，不是 `retained`：如果取两者中更强的那个，就等于让留存的那一半把实时的那一半"洗白"成了一个它自己没挣到的等级。
>
> 这根轴不是在层级（1/2/3 级）之上又加的第四级，`policy.py` 自己的注释把理由说得很直接：层级编码的是证据有多新、有多深——全国级监测、tile 级分析、交叉视角证据；可验证性编码的是层级完全没有涉及的另一件事——一个读者、而不是本项目自己，能独立做什么来核实一份依据。一次 Places 查询可以就此刻某个地点的设施情况给出答案，分辨率也是这个数据源能支持的最细粒度，但它依然可能落在这根轴的最底端，因为没有 Google Maps Platform 密钥的任何人都无法把它重放一遍。"当下且准确"是层级要回答的问题；"项目之外的人能不能核实"是可验证性要回答的问题，同一个事实完全可能在前者上得分很高、在后者上得分很低。

## Two regimes, because re-derivation needs determinism

The first regime covers structured, deterministic responses — Places' `searchNearby`, and any future adapter over an API that returns the same JSON for the same request. `response_digest(payload: Any) -> str` in `src/geosteward/live/base.py` is the anchor: a sha256 over the payload serialized as canonical JSON, with sorted keys and no incidental whitespace, so a provider reordering its own keys between calls does not read as a change of content. A reader with their own key would re-issue the same request — the request is entirely the project's own, since it chose the H3 cell, the radius, and the field mask, and nothing about it depends on the provider — and would compare the digest they get to the one recorded. `compare_digests(recorded_sha256: str, replayed_sha256: str) -> dict[str, Any]` in `src/geosteward/live/record.py` is deliberate about what a mismatch means: it reports `verdict: "drift"`, not an error, because a changed digest most often means a facility opened, closed, or was reclassified — the provider's data moved, which is exactly the kind of thing a reader checking a disaster product wants to learn, not a failure to bury.

The second regime covers model-generated prose grounded in third-party references — `GroundedMapsSource.ask` in `src/geosteward/live/grounded.py`, wrapping a call to Gemini's `generateContent` with the Google Maps grounding tool attached. Nothing here is reproducible the way a Places response is: a grounded answer varies across model versions even at temperature 0, so a digest over the text would not anchor anything — it would look exactly like `response_digest`'s output while attesting to nothing, which is worse than carrying no digest at all, because somebody would eventually cite it as if it meant something. `GroundedResult` in `src/geosteward/live/base.py` is built with that absence stated as the design rather than as an oversight the code happened to leave in; its docstring reads, "No `response_sha256`, and that absence is the point... What survives is the citations," and the dataclass itself carries only `text: str` and `citations: tuple[str, ...]` — there is no digest field to fill in, not merely a field left blank. `tests/test_live_adapters.py`'s `test_result_has_no_digest_field_to_mistake_for_an_anchor` checks the absence directly with `self.assertFalse(hasattr(result, "response_sha256"))`, so a later edit cannot quietly reintroduce one without a test noticing.

A `cited-only` answer therefore rests on citations alone, and the claim plane treats it accordingly: neither `deny-damage-assessment-without-retained-evidence` nor `allow-facility-context-re-derivable` — the two rules `03` covers in full — ever authorizes `cited-only` for anything. A grounded facility answer matches no allow rule in `policy_v1.yaml` and falls through to `default-deny`, without a line of policy ever having been written to refuse it by name. The distribution plane reasons about the same third-party boundary from the publishing side, through the `license` attribute `04` covers; the record this chapter describes next is what `license: project` looks like when the artifact it labels holds a live source's attestation rather than its content.

> **中文。** 第一种机制覆盖结构化、确定性的响应——Places 的 `searchNearby`，以及将来任何一个"同样的请求总是返回同样 JSON"的 API 适配器。`src/geosteward/live/base.py` 里的
> `response_digest(payload: Any) -> str` 就是那个锚点：对响应体做规范化 JSON 序列化（键排序、不带多余空白）之后取 sha256，这样即使数据源提供方在两次调用之间调换了自己 JSON 里键的顺序，也不会被读成内容变了。一个拿着自己密钥的读者可以重新发出同一个请求——这个请求完全是本项目自己的，因为选定 H3 单元格、半径、字段掩码的都是本项目，和数据源提供方无关——再把自己算出来的摘要和记录下来的那个做对比。`src/geosteward/live/record.py` 里的
> `compare_digests(recorded_sha256: str, replayed_sha256: str) -> dict[str, Any]` 对"不一致意味着什么"很讲究：它报告的是 `verdict: "drift"`（漂移），不是一个错误，因为摘要变化多半意味着某个设施开张、关闭或者被重新分类了——是数据源提供方那边的数据动了，这正是一个核查灾害产品的读者想知道的事，不该被当成失败埋起来。
>
> 第二种机制覆盖的是锚定在第三方参考资料上生成的模型文字（grounded generation：让模型的回答有依据地引用检索到的第三方资料，而不是凭空生成）——`src/geosteward/live/grounded.py` 里的

> `response_digest` 的输出一模一样，实际什么都没证明，这比压根不给摘要更糟，因为总会有人把它当真去引用。`src/geosteward/live/base.py` 里的 `GroundedResult` 把这个"没有摘要"处理成设计本身，而不是代码顺手落下的疏漏：它的文档字符串写着"没有
> `response_sha256`，这个缺失正是重点……能留下来的是引证"；这个 dataclass 本身也只带 `text: str` 和
> `citations: tuple[str, ...]` 两个字段——不是一个空着没填的摘要字段，而是压根没有这个字段。`tests/test_live_adapters.py` 里的
> `test_result_has_no_digest_field_to_mistake_for_an_anchor` 直接用
> `self.assertFalse(hasattr(result, "response_sha256"))` 检查这个缺失，这样以后哪怕有人悄悄想把它加回来，也会被这个测试拦下来。
>
> 因此一个 `cited-only`（仅可引证）的回答只能靠引证本身立住，断言平面对它的处理也是照此办理：`03` 章完整讲过的那两条规则——`deny-damage-assessment-without-retained-evidence` 和
> `allow-facility-context-re-derivable`——没有一条会授权任何 `cited-only` 的东西。一个经过 grounding 的设施回答不会命中 `policy_v1.yaml` 里任何一条允许规则，只会落到 `default-deny`，而这背后甚至没有专门为它写过一行拒绝它的策略。发布平面从发布的一侧，通过 `04` 章讲的 `license` 属性，处理的是同一个第三方边界；本章接下来要讲的记录，正是当一个制品装的是实时数据源的证明、而不是它的内容时，`license: project` 长什么样。

## The record is publishable because it is empty

`04`'s `artifact_classes` table classifies the file `LiveEvidenceRecorder.record` writes as `live_lookup_record`, `{resolution_cap: tile, audience: public, license: project}`; this section is about what fills that file, not about the classification itself. When `LiveEvidenceRecorder.record` in `src/geosteward/live/record.py` writes one row to `events/live_evidence.jsonl`, that row holds the request — entirely the project's own, since it chose the cell, the radius, and the field mask — a `response_sha256`, an `n_results` count, and the source's own `license`, `verifiability`, `retention`, and `attribution` declarations. `RECORDED_KEYS` in the same module names exactly these nine keys and nothing else. A reader who obtained their own Places key could read the request straight off a row, re-issue it, and run the response through `response_digest` themselves; matching the recorded `response_sha256` is what `compare_digests` calls `re-derived`. The row is publishable precisely because none of the third-party content the request produced is in it — the module's own docstring states this as the design rather than a side effect: "It is publishable because it is empty of the content it attests to."

Place IDs are the one field the response returns that the row deliberately never carries, and the omission was an owner ruling rather than an accident of what the code happened to write (§11.2 of `docs/design/specs/2026-08-20-non-retainable-evidence-design.md`): the terms permit storing place IDs indefinitely, but permission to store is not obviously permission to redistribute in a public artifact, and the design treats that as a question worth a deliberate answer rather than a default. `LiveResult.reference_ids` in `src/geosteward/live/base.py` carries the IDs forward for the project's own joins — they are real and kept, just never published — and `build_payload` in `record.py` never reads `result.reference_ids` at all, so there is no code path by which one could reach the written row. `tests/test_live_record.py`'s `test_place_ids_are_absent_from_the_record` is the check: it first confirms `result.reference_ids` is non-empty, so the test is not vacuously true, and then asserts that none of those IDs appear anywhere in the JSON-serialized payload.

`build_payload` builds the row from a named key list rather than from `asdict(result)` or `**kwargs`, and that choice is enforced rather than stylistic: every value is read off `source` and `result` by name, and the assembled dict is checked against `RECORDED_KEYS` on every single call, raising `RecordShapeError` if a key is missing or a key nobody approved appears. The same function also requires the request to name an `h3_cell` (`REQUIRED_REQUEST_PARAMETER`), refusing with `RecordShapeError` otherwise: `live_lookup_record` is classified at tile resolution, and a row carrying an exact latitude and longitude would contradict its own classification the moment a reader opened it. `tests/test_live_record.py`'s `test_request_without_a_tile_is_refused_rather_than_recorded` drives a point-shaped request through `build_payload` and checks that the raised exception names `h3_cell`.

What reaches the model is thinner still than what the row keeps. `LiveSource.summarize` in `src/geosteward/live/base.py` is documented to return "Counts by category — never names, ratings, or numbers" — `hospital=1, fire_station=1 within 1200 m`, for instance — and `PlacesSource.summarize` in `src/geosteward/live/places.py` implements exactly that, discarding everything about each place except its `primaryType`. The reason is stated in `base.py`'s own docstring: retention and onward disclosure are different questions, and handing third-party content to a hosted model endpoint is onward disclosure, which the licence does not obviously settle in the project's favour just because the content never touched a disk. Counts are the project's own derived numbers rather than the provider's content, so they cross that boundary without raising the question a name or a rating would.

> **中文。** `04` 章的 `artifact_classes` 表把 `LiveEvidenceRecorder.record` 写出来的这份文件分类为
> `live_lookup_record`，`{resolution_cap: tile, audience: public, license: project}`；本节讲的是这份文件里装了什么，不是这项分类本身。`src/geosteward/live/record.py` 里的

> `test_request_without_a_tile_is_refused_rather_than_recorded` 就拿一个点状请求去跑

## What is enforced, and by what test

`tests/test_live_record.py`'s `TestContainment.test_no_poison_string_reaches_the_written_record` is the load-bearing test of this design, and its shape is a direct answer to the 2026-08-20 publication-boundary incident chapters `03` and `04` both trace their own second rule set back to: that failure was not a wrong rule, it was a correct constraint nothing ever read. So this test does not leave "the record cannot contain restricted content" as an intention — it drives the recorder for real and checks the bytes. `FakeLiveSource` in `src/geosteward/live/fake.py` is seeded by default with `POISON_PAYLOAD`: a fabricated hospital, school, and fire station carrying exactly the kinds of content the licence forbids warehousing — display names, phone numbers, ratings, rating counts, and place IDs — every string chosen to be loud enough (`Mulholland Poisonstring Medical Center`, `(555) 013-0117`, `PLACEID_POISON_AAA`) that it could not plausibly occur anywhere else in the repository by accident. The test looks up that payload, records it through the real `LiveEvidenceRecorder`, reads the bytes actually written to a temporary `live_evidence.jsonl`, and asserts that every one of the ten `POISON_STRINGS` — the content values, not the field names that carry them — is absent from those bytes. A first assertion, `self.assertIn("Poisonstring", json.dumps(result.display_payload))`, confirms the poison genuinely reached the recorder, so the test cannot pass by never exercising the risk it exists to catch.

Bare numeric content — a rating of `4.7`, a count of `812` — is deliberately absent from `POISON_STRINGS`, and `fake.py`'s own comment explains why: a short digit string can occur inside a 64-character hex digest by chance, and a containment test that fails on the day a hash happens to contain one teaches people to stop trusting it. That gap is covered two other ways instead: the phone numbers on the list are distinctive enough to grep for reliably, and `RECORDED_KEYS`'s exact-key assertion in `build_payload` is the guarantee that actually generalises — any field nobody approved fails the write regardless of what value it carries, numeric or not.

## Never run against a live API

Neither live adapter has ever run against a live API. `PlacesSource` in `src/geosteward/live/places.py` and `GroundedMapsSource` in `src/geosteward/live/grounded.py` both say so in their own module docstrings — "Unverified against the live API" — and the reason is concrete rather than a hedge: there is no GMP (Google Maps Platform) key, and no Gemini key, configured anywhere this project runs (`docs/design/specs/2026-08-20-non-retainable-evidence-design.md`, §10, blocker 1). `tests/test_live_adapters.py` drives both adapters against `StubServer`, an in-process HTTP server the test module itself starts and tears down, matching exactly the request and response shapes this code expects — which pins down how `places.py` and `grounded.py` behave against a shape someone else chose, and establishes nothing about how Google's servers actually respond. `events/live_evidence.jsonl` — the record this chapter has spent most of its length describing — does not exist outside tests, present only inside a test's own temporary directory and never written anywhere in this repository. `scripts/manual_anchors.py` cites the path in `DECLARED_ABSENT` for exactly this reason, so this chapter can name it without the anchor gate treating its absence as a broken link.

That gap is not a footnote to the rest of this chapter; it is the fact that keeps everything above honest. Every claim this chapter makes about re-derivation, digests, and containment describes this code's own tested behaviour against a stub it controls — a real test of a real property, but a property of this project's plumbing, not of Google's API. Whether a real Places response actually canonicalizes the way `response_digest` assumes, whether a real Gemini grounding call actually returns the `groundingMetadata` shape `grounded.py` parses, and whether the numbers this design promises hold up against a live account are all still open. The design document says so in the same terms this chapter does: the measured numbers belong in that document once the mechanism has run for real, not before.
